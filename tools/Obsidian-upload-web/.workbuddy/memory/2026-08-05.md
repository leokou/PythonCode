## 修复：预览区末尾回车后最后一行不可见
- 现象：预览区（contenteditable `#preview` / `.preview-body`）在文档最后一行按回车，新空行被裁切在窗口底部之外看不到。
- 根因：`_doPreviewEnter` 插入 trailing `<br>` 后调用 `_scrollPreviewCursorIntoView()`；但末尾 `<br>` 不增加块高度，`getBoundingClientRect` 测不到需要滚动，`delta=0` 不滚动。

  - `_scrollPreviewCursorIntoView()` 在末尾场景下直接 `previewEl.scrollTop = maxScroll` 滚到预览区底部。
- 配套（`frontend/style.css`）：`.preview-body` 的 `padding` 由 `16px 22px` 改为 `16px 22px 32px`，保证光标行不贴底边可见。

## 补丁2：抑制 editor→preview 滚动同步覆盖（commit 79a32c4）
- 问题：补丁1虽把预览区滚到底，但 `cursorFollowPlugin`（dispatch 后 rAF 执行 `_ensureEditorCursorVisible`）会滚动编辑器，其 `scroll` 事件触发 editor→preview 同步 `scrollPreviewToLine(line)`，把预览区拉离底部 → 新行再次出窗。

## 补丁3：收窄抑制范围到末尾回车（commit 7de30e6）
- 回归：补丁2把 `_cursorSyncActive` 用到【所有】预览滚动（200ms），导致中段编辑时 editor↔preview 滚动同步被掐断，引发：①回车要按两次才出新行 ②回车后预览跳到别处 ③删除跑别处删错内容。
- 修复：`_scrollPreviewCursorIntoView` 加 `needGuard` 标志，仅【末尾回车滚到底】时置 `_cursorSyncActive`；中段滚动不再设 guard，恢复原有双向滚动同步。

- 验证待用户确认：中段回车一次出一行、回车后不跳位、删除定位正确。

## 补丁4：跳过 <br> 插入的杂散 input，修复回车后编辑区多出空行（commit ed35469）
- 回归：补丁3解决删除/跳位后，回车仍有 bug——编辑区（markdown）出现大量预览区没有的空行，两侧内容不对齐。
- 根因：`_doPreviewEnter` 分两步操作——dispatch 在 markdown 插入 `\n`（第1步）+ `range.insertNode(br)` 在 DOM 插入 `<br>`（第2步）。第2步会**异步派发 `input` 事件**，而 `_previewEditing` 在第1步后同步重置为 false → 该 input 被 `_syncPreviewToEditor` 处理 → 检测 `innerText` 中的 `<br>` 换行为"新增内容" → 向 markdown 追加多余 `\n` → 每按一次回车积累一个空行。
- 修复：`_skipPreviewRerender` 立即恢复，`_previewEditing` 改为 `setTimeout(0)` 延缓恢复——让 `<br>` 的 `input` 事件在 `_previewEditing=true` 期间被跳过；后续用户真实输入（键入/删除）正常走 diff 同步。
- 已验证：`_oldBlockPlainText`（innerText 读取强制 layout）与延时后的 newPlainText 一致，不存在「基线过期导致下次输入同步错误」风险。

## 补丁7：预览区撤销栈根本性修复（commit 4b32766）
四类缺陷，前六个补丁全在治滚动症状，真正原因是撤销栈根本没在记录：
1. **栈只存一个快照**：`input` 监听器用 `_previewInputActive` 门控「仅首次输入存快照」，而该标志只在 `blur` 重置 → 一次 focus 期间栈里永远只有 1 个快照 → 首次 Ctrl+Z 直接跳回进预览区时的状态（像乱跳），第二次 `pop()` 返回 undefined 早退 → **完全无反应**。修：每次 input 都调 `_savePreviewHistory()`，函数内按「与栈顶内容相同则跳过」去重，自动合并同一输入会话。
2. **判空用 `!newDoc`**：空文档快照是 `""`，`!""` 为 true → 被误判栈空 → 撤销回空文档永远做不到。改 `=== undefined`。
3. **切 Tab 不清栈**：`_previewHistory` 是全局的 → Ctrl+Z 会把上个 Tab 的整篇内容写进当前 Tab。新增 `_clearPreviewHistory()`，`switchTab` 内 `activeTabId = id` 后立即调用。
4. **pending debounce sync 未处理**：`input` 挂 200ms `_syncPreviewToEditor`。若用户在 200ms 内按 Ctrl+Z → `tab.state.doc` 尚未含最新输入 → pop 出的快照与当前 doc 相同（撤销"无效果"），且 200ms 到点后 pending sync 仍执行 → 把 DOM 写回 markdown → **覆盖掉撤销结果**。修：`_doPreviewUndoRedo` 与 `_doPreviewEnter` 入口均先 `clearTimeout` + 立即 `_syncPreviewToEditor()` flush；`_syncPreviewToEditor` 进入即 `_previewSyncTimer = null`（debounce 触发后旧 id 仍 truthy 会让外部误判重复 flush）。

## 补丁8：撤销时编辑区乱飘（commit 990867a）
撤销可用后残留问题：预览区 Ctrl+Z 后编辑区一路滚到文末。
- 根因：`_doPreviewUndoRedo` 全文替换 dispatch 设 `selection.anchor = newDoc.length`（文档末尾）→ `cursorFollowPlugin` 在 rAF 中把编辑区滚到文末。`syncing` 只挡 scroll 事件的**反向同步**，挡不住编辑区**自身**滚动，这是之前几轮补丁一直漏掉的区别。
- 修复三点：① 新增 `_suppressCursorFollow`，`_ensureEditorCursorVisible` 入口判断，撤销期间编辑区不主动滚动；② 新增 `_commonPrefixLen`，光标落在新旧文档公共前缀末尾（= 撤销实际生效位置），不再落文末；③ dispatch 前存 `view.scrollDOM.scrollTop`，dispatch 后 + rAF 内各回位一次。标志在 rAF 链末释放 + 300ms setTimeout 兜底。
- 通用经验：**CM6 里「抑制滚动同步」和「抑制光标跟随滚动」是两件事**，全文替换 dispatch 必须显式指定 selection，否则光标默认落 0。

## 补丁9：跨区高亮重建 + 撤销定位变更行 + 顶部/底部双区同步（commit a498626）
用户反馈四点：删一个词后编辑区高亮消失要再点一下才亮、反向亦然、预览区 Ctrl+Z 定位不到撤回那行、小工具"回到顶部"只动编辑区。
- **高亮丢失根因**：两侧跨区高亮都是**纯 DOM class**，必然被重排抹掉——预览区 `renderPreview()` 重设 innerHTML 抹掉 `.cross-highlight`（且函数末尾还主动 `_clearCrossHighlight()`），编辑区 CM6 文档变更重建 `.cm-line` 抹掉 `.cm-crossHighlightLine`。而 `_highlightLine` 只由 mouseup / 方向键 / focus / click 触发，**打字和删除都不触发**，抹掉后没人重建。`_lastHighlightedLine` 此前只写不读，形同虚设。
- 修复：新增 `_findPreviewBlockByLine(line)`（从 `_highlightLine` 抽出）+ `_reapplyCrossHighlight()`（不改 `_lastHighlightedLine`、不滚动）；`renderPreview()` 末尾由 clear 改 reapply；`updateListener` 在 `docChanged` 时**先**把 `_lastHighlightedLine` 更新为编辑区光标行（必须在 `renderPreview()` 之前，否则那一帧闪旧高亮），**再**于 rAF 后重建编辑区侧 class。仅在此前已有高亮（`> 0`）时重建，不凭空产生。
- 撤销定位：补丁8 为止住乱飘把两侧视图完全冻结，副作用是看不出改了哪。现由 `anchor`（公共前缀末尾）算 `changeLine`，rAF 内先回位防闪 → nearest 语义仅在该行不在视口内时滚到 ratio 0.3 → 最后一个 rAF 里 `_highlightLine(changeLine)`（滚动后再高亮，CM6 虚拟化需目标行已渲染）。
- `editor_scroll_top` / `editor_scroll_bottom` 同时设 `previewEl.scrollTop`，前后 `syncing` 抑制 scroll 事件互相触发。
- 通用经验：**用 class 做的跨区高亮在任何会重建 DOM 的路径上都必须显式重建**；记录「当前高亮行」的变量若只写不读，就是一个还没被发现的 bug。

## 补丁10：跨块 Delete/Backspace 破坏下方格式（commit deafd34）

- 现象：预览区按 del 有时会破坏下面内容的格式。
- 根因：预览区**此前完全没有 Delete/Backspace 拦截**，跨块边界删除交由 contenteditable 原生处理。浏览器把下一块 DOM 合并进当前块，但 `_syncPreviewToEditor` 的 diff 只覆盖当前块的 markdown 行范围（lineStart 到下一块 data-line - 1）——合并进来的内容被当作「当前块末尾插入文本」写入，而下一块原本的 markdown 语法行（`## ` / `- ` / `> `）原封不动残留 → 内容重复、语法碎裂。
- 修复：新增 `_doPreviewDelete`，**仅在块边界接管**（块内删除仍走原生，行为零变化），在 markdown 层合并：删除 `[当前块内容末尾, 下一块首行末尾]`，插入剥离块级前缀后的纯内容，下一块剩余行不动。Backspace 在块首 == 上一块末尾按 Delete。
- 配套新增：`_isCaretAtBlockEdge` / `_getBlockLineRange` / `_stripBlockPrefix` / `_placeCursorInBlockAtOffset` / `_mergeBlocksInMarkdown`。
- **三个易错点（单测覆盖：26 条前缀 + 13 条合并场景全通过）**：
  1. 块行范围的 `endLine` = 「下一块 data-line - 1」，**通常落在块间空行上**。从空行末尾开始删会残留多余换行，使 ATX 标题这类单行块合并后仍被解析为独立块（视觉上「按了没反应」）。必须回退到块内最后一个非空行。
  2. 代码块/表格/分隔线剥前缀不安全 → `_stripBlockPrefix` 返回 null 拒绝合并 + 仍 preventDefault，宁可无响应也不破坏格式。
  3. flush pending sync 会触发 `renderPreview()` 重建 DOM，**使先前取到的 block 引用失效** → `indexOf` 返回 -1 → 静默退化回原生（修复形同虚设）。必须在 flush 后重新 `_findCursorBlock()`。
- 另：按 data-line 去重取最深嵌套（`<ul>` 与其首个 `<li>` 同 data-line，否则 Backspace 时 `blocks[idx-1]` 取到父级 ul → curLine === nextLine → 合并失败）；光标偏移用块 `innerText` 精确长度，不用 markdown 行长度估算（会被 `**粗体**`、`[链接](url)` 等行内语法带偏）。
- **通用经验**：contenteditable 上任何会跨越块边界的编辑操作（Enter / Delete / Backspace / 粘贴），都必须在 markdown 层接管；交给浏览器原生 = 块级语法必然丢失，因为 diff 同步的作用域是单个块。

## 补丁11：跨区高亮跳到上一次编辑位置（commit b6eeea5）

- 现象：在预览区删掉一行里的某个词，编辑区高亮跳到别的行去了，「感觉跳到上一次删除的位置」。
- 根因：补丁9 在 `updateListener` 里用 `update.state.selection.main.head` 推导高亮行，注释中的假设「预览区来源的变更经 CM6 change mapping 后光标同样落在编辑点」**是错的**。`_syncPreviewToEditor` 的 dispatch 不设 `selection`，CM6 的 change mapping 只把旧 selection 按 changes **平移**，不会把光标移到编辑点 → 读到的是编辑器光标的陈旧位置（上次编辑器操作留下的地方）。
- 修复：改用 `update.changes.iterChangedRanges((fromA,toA,fromB,toB) => ...)` 取第一处变更范围，并在范围内再比对新旧文本的**公共前缀**定位到真正改动的字符，再 `doc.lineAt()` 换算行号。
- **必须做公共前缀细化**，变更范围本身粒度太粗：`_applyDiffToMarkdown` 是整块替换（`fromB` 指向块首行 → 多行段落改末行会高亮到首行）；`_doPreviewUndoRedo` / `_doFullReplace` 是整篇替换（`fromB` 恒为 0 → 高亮被拽到第 1 行）。
- 单测 8 场景通过：最小 change 删词 / 整块替换 / 整篇替换（改中段与改首行）/ 纯插入 / 整行删空 / 多行块改第 2 行 / 中文多字节。
- **通用经验**：CM6 中「本次改了哪」的唯一可靠来源是 `update.changes`，不是 `state.selection`。只要 dispatch 没显式设 selection，光标位置就是上一次操作的残留值，任何依赖它推导「当前编辑位置」的逻辑都会读到陈旧数据。

**架构结论（已向用户提出，用户选择先修不重构）**：预览区是双真相源（markdown 文本 + contenteditable DOM 各自可编辑，靠 diff 双向反推），而 markdown→HTML 是有损非双射映射，这类 bug 无法靠补丁根治。实测耦合度：7 个全局 boolean 标志 61 处引用、11 个 previewEl 监听器（含 2 个职责分裂的 keydown）、~400 行反向同步链路、CLAUDE.md 517–539 专写陷阱手册。
建议方案：**A. 预览区改只读**（净删 900–1200 行，1–2h，消除全部此类 bug，代价是不能在预览区打字）；B. CM6 Live Preview（Decoration 就地渲染，单真相源，2–4 天）。不要选「重写但仍保持双真相源」。

- 根因：预览区→编辑器同步（`_syncPreviewToEditor` / `_mergeBlocksInMarkdown` / `_doPreviewEnter` / `_doFullReplace`）调用 `view.dispatch(...)` 会抢占编辑器焦点 → 编辑器 `focus` 监听（`script.js:2501`）触发 `_highlightLine(lineNum,"preview")` → `scrollPreviewToLine` 把预览滚到编辑器光标行。而编辑器 `selection.main.head` 是陈旧位置（= Outline 始终高亮的行），故预览跳到该处；若编辑器因选区被映射而滚动，`view.scrollDOM` 的 `scroll` 监听也会把预览拖过去。
- 修复（`frontend/script.js`）：
  - 新增标志 `_previewSyncActive`；预览区驱动的同步期间置 `true`，屏蔽编辑器 `focus` 监听的 `_highlightLine` 滚动与 `view.scrollDOM` 的 `scroll` 监听传播。
  - 四处 dispatch 前设 `true`、末尾 `previewEl.focus()` 后 `requestAnimationFrame(() => _previewSyncActive=false)` 复位。
  - 补 `_mergeBlocksInMarkdown` / `_doPreviewEnter` 缺失的 `previewEl.focus()`（此前焦点遗留编辑器，是 bug 来源之一）。
- 验证：`node --check` 通过。CLAUDE.md 红线：未自动打包 EXE，需本地 `build.bat` 生效。
- 遗留（已解决，见文末「预览区删除→编辑区跳页首」）：目录高亮由 `Outline.highlightAtPos(update.state.selection.main.head)` 驱动，编辑预览时跟随编辑器陈旧/顶部选区 → 仍会高亮一级标题；最终在 `updateListener` 加 `_inPreviewSync()` 守卫解决。

## 优化：资源管理器收窄时文件夹名被压成单字
- 现象：工作区资源管理器（#pane-workspace）拖到较窄宽度后，嵌套文件夹名被截断成 1 个字，右侧仍有较多留白。
- 根因：`.exp-children` 每层缩进 `padding-left: 2em`（约 25px/层），在 160–200px 面板下 2–3 层嵌套后名字可用宽度仅剩 20–60px，并被 `.exp-row` 的 6px 水平 padding 进一步压缩。

## 修复：预览区删除 → 编辑区跳页首 + 目录高亮一级标题（commit 待提交）
- 现象（用户复现，授权自测）：在**预览区**删除内容后，①目录（Outline）高亮到「一级标题」(H1)、②编辑区（CM6）直接跳到页首、③预览区正常未跳。与早期"删除→预览跳"方向相反，属同一类「反向同步期间编辑器陈旧选区被当真」的竞态。
- 根因：预览→编辑器反向同步 `_syncPreviewToEditor` 的 `view.dispatch({changes})` 触发编辑器 `updateListener` 与 `cursorFollowPlugin`，二者在同步窗口内**缺乏 `_inPreviewSync()` 守卫**：

- 修复（`frontend/script.js`，编辑器侧、未触预览渲染核心，符合红线）：
  - `updateListener` 的 TOC 分支包 `if(!_inPreviewSync()){ Outline.highlightAtPos(head) }`；同步结束后用户真实光标/输入仍正常驱动目录。
